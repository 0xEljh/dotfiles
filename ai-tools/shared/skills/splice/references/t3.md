# Coordinate a Splice run in T3

Read before execution or resume. Discover live tool schemas. Names may have a
server prefix. Managed worktrees start at the coordinator's committed `HEAD`.
Workers adopt exact commits by fast-forward. Explicit managed launch bases and
standalone OpenCode orchestration are unsupported.

## Check capabilities

Call `orchestrator_capabilities`. Record `parentThreadId` as `ownerThreadId`, the
OpenCode provider instance, model, permission modes, and constraints. The
coordinator may use another provider. Do not infer these results for other adapters.

Inspect saved worktree setup scripts and invoked hooks. Dependent adoption
requires absent or worktree-local, safely repeatable setup. Unknown external
effects, migrations, or shared database seeding block adoption. A rerun cannot
undo initial effects.

Before the first delivery run on a runtime configuration, probe a disposable
repository. Get permission for side effects. Record versions, settings, commands,
identities, and observations:

1. Launch an isolated managed OpenCode task. Verify its native session has no
   `parentID` and uses the ordinary coding role and instructions. T3's
   `parentThreadId` is not OpenCode ancestry. Mark uninspectable identity unverified.
2. Authorize and exercise native exploration and review delegation. Confirm results
   arrive and the worker retains its normal workflow.
3. Read the child's `branch` and `worktreePath` with `t3_thread_read`. Verify the
   repository, launch commit, object visibility, branch-preserving fast-forward
   adoption, and safe setup and verification after adoption.
4. Observe completion with nested work, later queued work, and cancellation.
   Check `workState`, `hasPendingChildRuns`, later terminal results, and whether
   cancellation stops owned nested execution.
5. With separately authorized disposable PRs, check linking and settlement.
   Inspect `sidebarAutoSettleOnMerge` and project overrides without changing them.

Reuse evidence only while adapter, permissions, setup, and settlement settings
remain unchanged. Mismatched or partial probes block delivery and automatic
merge-first continuation, not planning or brief preparation. Source inspection
does not replace a live probe.

## Track the work

Use the approved breakdown as the coordinator's working notes. A short table is
enough: workstream, dependency, worker link, PR, and status or next action. Save
local notes only if needed for resume. Keep them untracked and free of secrets.

Retain `taskId` for status and cancellation, `childThreadId` for the worker link,
and the launch request key for retries. Read other metadata from T3 or the PR host
when needed. Do not invent run or attempt IDs, copy API responses into a ledger,
or pass this bookkeeping to workers.

Link workers as `[title](t3-thread://v1/<childThreadId>)` using the exact returned
ID. Keep one active coordinator. `pr_ready` means the required delivery evidence
has passed, not that the PR is merged or approved for merge.

## Launch

1. Reconcile existing work. Check ownership, dependencies, concurrency, setup,
   and permissions. Pause if coordinator `HEAD` differs from the approved baseline.
   Do not commit unrelated work or move `HEAD` to manufacture a base.
2. Prepare the [worker brief](worker-brief.md). For dependent work, verify the
   predecessor with the PR host and pin the starting commit. Ordinary independent
   work needs no extra starting-point instructions.
3. Save the request and a stable `clientRequestId` before `delegate_task`. Set
   `isolation: "worktree"`, the selected provider and model, the full brief as
   `task`, and normally `mode: "async"`.
   T3's `role` field does not authorize a restricted native implementer profile.
4. Keep the returned task and worker links. Use `t3_thread_read` for the assigned
   branch or worktree when needed, especially for a stacked PR base. Missing values
   during preparation are not permission to guess or relaunch. T3 may rename
   generated branches. Read their current names rather than renaming them.

T3 assigns the branch and checkout. Uncommitted edits are not copied. Each
replacement needs a new managed checkout and distinct branch. Replaying a key
is the same attempt.

If the response is lost, replay only the identical payload and key within the
tool's supported owner scope. Conflicts, uncertain replay guarantees, or ambiguous
bindings block relaunch. Retry guarantees do not transfer between coordinators.

For dependent work, include only the brief's conditional adoption instructions.
Use a pinned commit, not a moving branch tip. If it is missing locally, fetch that
commit from the approved remote or ask. Non-fast-forward adoption blocks. Do not
combine divergent predecessors implicitly.

Async completion wakes the coordinator. End the turn when only outstanding tasks
remain. Use `task_status` during active work or explicit resume, not polling,
timers, or custom watchers.

## Release dependencies

On completion, resume, a `pr_ready` decision, or dependent release, query the task
and authoritative PR host again. Cached links and worker handoffs are insufficient.

- **Task:** require success, settled nested work, and no pending child runs.
  Inspect `latestTerminal*` and the child timeline for later work. The original
  terminal result alone cannot settle it. Stopped, ambiguous, failed, or live work
  does not release dependencies.
- **PR:** verify repository, number, head repository and branch, base branch,
  pushed head, and base against the approved work. Require passing CI and host
  approvals wherever the plan or repository requires them. Pending, missing,
  unknown, or API-error states block. Record justified not-applicable decisions
  for checks or approvals that neither requires.
- **Evidence:** match acceptance, local verification, and required review
  dispositions to that head. Have the worker resolve gaps or failures.

For follow-up in the same worker conversation, use the live `t3_thread_send`
contract and retain returned task IDs. This remains the same attempt. New
independent review rounds use fresh `delegate_task` calls, not reviewer-thread
messages. Reconcile all pending work before release.

Head movement invalidates verification. Predecessor or base movement blocks
affected release until ancestry, scope, and verification are reconciled. Recheck
on resume. Use tool and host evidence rather than worker-written metadata reports.

Choose each relationship separately:

- **Independent:** both workers start at the approved baseline and may target the
  same base.
- **Stacked:** B waits for A's `pr_ready`, adopts A's verified pushed head, and
  targets A's actual branch. Repeat for further layers. Revalidate the affected
  chain after movement. If fast-forward reconciliation is impossible, get approval
  for replacement or a strategy change, not an implicit rebase.
- **Merge-first:** wait for host-observed `merged`. Pin a locally resolvable commit
  containing the merge result, verified with Git. Follow the approved target-base
  and commit-resolution rule, including squash or rebase results. Open predecessors
  are `blocked: awaiting_merge`. Closed unmerged predecessors need a decision.
  Divergent unmerged prerequisites must merge first. A PR has one comparison base.

Assign warranted combined verification to a workstream or post-merge check.
Passing isolated tests does not verify the combination.

## Link PRs and wait for merges

Workers link PRs in their own threads. The coordinator calls
`link_pull_request({threadId: ownerThreadId, url})` for every run PR as soon as it
starts coordinating that PR, including every stack layer. Before handoff, call
`list_thread_pull_requests` for the owner and link missing run PRs. Report linking
failures. Exclude unrelated background PRs.

Linking authorizes neither merging nor monitoring. Default to explicit resume
after merges. All linked PRs becoming terminal may settle the coordinator while
dependents are still planned. Settlement does not delete the run or guarantee
continuation.

If monitoring is requested, call `watch_pull_request` and end the turn. On a wake,
reconcile host state before scheduling. Watch completion or thread settlement is
not merge evidence. Call `unwatch_pull_request` before handoff.

## Resume, cancel, or recover

Resume in the original coordinator thread. Reconcile worker links, tasks, pending
work, and affected PRs before launching. Duplicate wakes do not authorize new
workers. Parent-scoped task ownership cannot transfer to another thread.

After a crash, resume the original conversation. If unavailable, stop scheduling.
Ask the operator to stop recorded workers through T3 and verify queued work and
external jobs are inactive. Unreachable work stays blocked. Confirm cessation and
get approval before launching replacements in fresh checkouts. Do not claim
ownership of old tasks.

On human takeover, note which work is no longer coordinator-managed. Suspend its
scheduling and automatic cancellation until explicitly reconciled.

To cancel owned work, use `task_cancel` with its saved task ID.
Cancellation covers later child turns and delegated tasks. Query task and thread
state afterward. An old terminal status alone proves nothing. Require no pending
child runs or live execution, and account for external jobs separately. Confirm
cessation and replacement authority before replacing. A stopped queue may still
need human action.

T3 owns worktree creation and removal. Offer cleanup after handoff. Get approval
and verify no live or human-owned work remains before removal. Retain failed,
cancelled, and unmerged work and coordinator notes unless removal is approved.
Do not reuse cancelled branches.

## Use an explicitly chosen alternative

Ordinary top-level conversations require an approved plan change. Use
`t3_thread_launch` with explicit `workspaceStrategy` and `message`. First save
intent, a unique token included in the title, exact base, and requested branch.
Retain the thread ID and inspect preparation and binding with `t3_thread_read`.

After a lost response, find the intent in threads and worktrees and verify binding
before relaunch. Ambiguity blocks. This mode has no managed retry, exactly-once
launch, completion-wake, or parent-cancellation guarantee. Use explicit resume or
bounded waits. A failed capability check is not permission to switch modes.
